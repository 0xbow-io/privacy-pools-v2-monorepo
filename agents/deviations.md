# Intentional Deviations Register (`INTL-NN`)

Deviations from spec / convention that are **deliberate and accepted**, so they are not
re-flagged as findings on every quality-loop pass. Each entry: what, why, where, who/when.
An item here must be a *conscious* decision — if it's just unfixed, it's a finding, not a
deviation.

### Relayed key-registration (#310/INTL-05) full-review r1 residuals (2026-07-10)
- **G3** (Medium test-gap, ACCEPTED) — the relayer→contract register-and-relay wire is exercised only
  with a stubbed `simulateContract`; no anvil/fork e2e. Accepted: funds-safety on this wire is covered by
  the contract's own real-proof `RegisterAndRelay.t.sol`, and the relayer leg is a thin viem dispatch whose
  arg construction is covered by the chain-service unit test + the new G1/G2 tests. A gated fork e2e belongs
  in `packages/relayer/e2e/` (a separate boundary), owned by whoever holds that directory.
- **L-1** (Low, ACCEPTED) — predicted-post-insertion keystore-root staleness race: a concurrent keystore
  mutation shifts the insertion index so the predicted root ≠ real root and the atomic bundle reverts.
  Strictly griefing, never a soundness break (the pool accepts only real known roots; Groth16 proves
  membership independently). Documented on-chain; no on-chain fix exists. Mitigation = private orderflow.
- **L-2** (Low, ACCEPTED — gating reverted) — `Keystore.initializeEIP712()` (reinitializer(2)) is
  unpermissioned. Not exploitable: no params, only hardcoded constants, runs once, and a revert rolls back
  the version bump (no lockout). Gating it with `UPGRADER_ROLE` was implemented then reverted — it ripples
  into `Keystore.t.sol` + `Keystore.tree` + a new access test + bulloak, exactly the keystore files the
  concurrent instance owns, a disproportionate churn/conflict cost for a non-exploitable Info item.
- **L-3** (Info, ACCEPTED) — `setAuthPolicyWithSig` has a deadline but no per-account nonce, so a
  signed-but-unsubmitted authorization can't be revoked before its deadline. Bounded by the account-chosen
  deadline + the one-time `nullifyingKeys` guard (only ever installs the account's own signed key).
- **RR-1 note:** the standalone `submitRelayedRegistration` SDK method now throws `RelayerRequestFailed`
  up front (the relayer exposes no standalone `register` route — that endpoint remains the INTL-05 deferral
  pending the fee-commitment economics of a fee-less registration); the atomic `relayRegisterAndWithdrawal`
  path is the supported one.

### Batch full-review r1 accepted-Low residuals (2026-07-10)
- **B-1** (Low) — `PrivacyPoolRelay` checks `_MAX_BATCH < pool.rootHistorySize()` only at its own
  construction. The pool is UUPS-upgradeable, so a future upgrade that shrank the state-root buffer
  below `_MAX_BATCH + 1` would break the shared-pre-batch-root guarantee. **Accepted:** liveness-only
  (a near-max batch would revert `PoolVault_UnknownStateRoot`; funds are never at risk), and the
  relayer independently re-checks the coupling live before every batch (`assertBatchFitsRootHistory`).
- **BW-3** — batch is full-balance only; no partial/subset multi-note batch. Accepted intentional
  scope (the feature is "withdraw the whole single-asset balance").
- **BW-4** — the submit→on-chain-revert race returns a `status=false` receipt rather than a thrown
  typed error. Accepted: notes correctly stay ACTIVE (not persisted); the pre-submit simulate covers
  the common case with a thrown `RelayerRejected`.
- **CR-2 / CR-5** (Nits) — extracting the shared per-item validation (CR-2) is a behavior-preserving
  refactor and `_distribute` is already shared; `receive()` placement (CR-5) predates the feature.
  Both skipped as out-of-scope cosmetics.
- **BW-2 note:** the self-submit batch gap was **built**, not deviated — see the batch full-review
  (`BATCH_FULL_REVIEW.md`); `relayBatch` is permissionless so the fix is SDK-only.
